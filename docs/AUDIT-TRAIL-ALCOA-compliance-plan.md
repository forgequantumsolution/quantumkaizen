# QuantumKaizen — ALCOA++ Compliant Audit Trail: Gap Analysis & Implementation Plan

Scope: a single, system-wide, tamper-evident audit trail that records **what changed, from what to what, by whom, when, from where, and why** — for every GxP-relevant action across QMS, DMS, LIMS, LMS, Workflow and Admin — plus the review, export and retention machinery that inspectors actually ask for.

Regulatory targets: **ALCOA++** (Attributable, Legible, Contemporaneous, Original, Accurate + Complete, Consistent, Enduring, Available + **Traceable**), **21 CFR Part 11** §11.10(e)/(d), §11.50, §11.70, §11.200, **EU GMP Annex 11** §9 + §12, **EU GMP Chapter 4**, **MHRA GxP Data Integrity Guidance 2018**.

## 3. Target architecture

Four layers, each one closing a class of gaps.

```
 HTTP request
    │
    ├─ requireAuth  ──► JWT { userId, email, sessionId, name }
    │
    ├─ auditContext middleware (AsyncLocalStorage)
    │     { userId, userName, employeeId, roleId, siteId, sessionId,
    │       ip, userAgent, requestId, reason?, signatureId? }
    │
    ├─ route handler → service → prisma (extended client)
    │        │                      │
    │        │                      └─ Layer 1: automatic capture
    │        │                         Prisma $extends query interceptor:
    │        │                         before-image + after-image → AuditEvent
    │        │                         (same interactive transaction)
    │        │
    │        └─ Layer 2: explicit semantic events
    │           recordAudit({ action: 'STAGE_TRANSITION', ... })
    │           for things a row-diff cannot express
    │
    └─ Layer 3: security events (login, logout, lockout, RBAC change, export)

 Layer 4: integrity + governance
   seq (bigserial) · prevHash · hash (SHA-256 chain) · DB triggers blocking
   UPDATE/DELETE · nightly chain verification job · monthly partitions ·
   audit-trail review records · export with e-signature manifestation
```

### 3.1 Why a Prisma extension for Layer 1

G1 says ~15 modules have no trail. Hand-writing ~400 `writeTrail` calls is slow *and* permanently leaky — the next feature forgets one and compliance silently regresses. A `$extends({ query: { $allModels: … } })` interceptor makes coverage **structural**: every `create/update/updateMany/upsert/delete/deleteMany` on an in-scope model produces an event, in the same transaction, or the business write fails. That directly answers "Complete" for an inspector: *the system cannot write GxP data without writing the trail.*

Explicit Layer-2 events stay for semantics a diff cannot carry: workflow stage transitions, approvals, rejections, e-signatures, report generation, bulk imports.

### 3.2 Model changes

Keep `AuditTrailEntry` as the table name so the existing 160 call sites keep compiling; add columns (all nullable at first, tightened after backfill).

```prisma
model AuditTrailEntry {
  id        String @id @default(uuid())
  seq       BigInt @default(autoincrement())   // gap-free ordering, tamper detection

  // WHAT
  entityType String
  entityId   String
  entityLabel String?        // human-readable ("SOP-014 rev 3", "TCK-1032")
  module     String          // QMS | DMS | LIMS | LMS | WORKFLOW | ADMIN | SECURITY
  action     AuditAction     // enum, see below
  field      String?
  oldValue   String?
  newValue   String?
  valueType  String?         // string | number | boolean | date | json | file
  diff       Json?           // full before/after for multi-field ops
  criticality AuditCriticality @default(NORMAL)  // NORMAL | CRITICAL — drives review

  // WHY
  reason      String?
  reasonCode  String?        // controlled vocabulary (data entry error, new info, …)
  signatureId String?        // FK-by-id to ESignature when the change was signed

  // WHO
  userId       String?
  userName     String        // denormalised, survives user deletion
  userEmployeeId String?
  userRole     String?
  userDepartment String?
  onBehalfOfId String?       // delegated/admin-on-behalf actions
  actorType    ActorType @default(USER)  // USER | SYSTEM | JOB | INTEGRATION

  // WHERE / HOW
  sessionId  String?
  ipAddress  String?
  userAgent  String?
  requestId  String?
  source     String?         // WEB | API | JOB | IMPORT

  // WHEN — server-side DB clock, UTC
  createdAt  DateTime @default(dbgenerated("now()")) @db.Timestamptz(6)
  clientTzOffsetMin Int?

  // INTEGRITY
  prevHash String?
  hash     String?

  @@index([entityType, entityId])
  @@index([createdAt])
  @@index([userId, createdAt])
  @@index([module, action, createdAt])
  @@index([criticality, createdAt])
}

enum AuditAction {
  CREATE UPDATE DELETE SOFT_DELETE RESTORE
  TRANSITION APPROVE REJECT SIGN
  LOGIN LOGIN_FAILED LOGOUT LOCKOUT PASSWORD_CHANGE PIN_ENROLL
  PERMISSION_GRANT PERMISSION_REVOKE ROLE_CHANGE
  VIEW EXPORT PRINT DOWNLOAD
  IMPORT ARCHIVE CONFIG_CHANGE
}
enum AuditCriticality { NORMAL CRITICAL }

```

  toSeq     BigInt

  verified  Boolean

`ESignature` additions: `recordHash` (SHA-256 of the signed record snapshot — binds signature to content, §11.70), `meaningCode` (controlled vocabulary), `auditEntryId`, `ipAddress`, `sessionId`, `signedAt @db.Timestamptz(6)`, `invalidatedAt`/`invalidationReason` (never delete).

### 3.3 Integrity chain

- `hash = SHA256(seq ‖ canonical_json(payload) ‖ prevHash)`; `prevHash` = hash of the previous entry **in the same daily chain partition** (`chainKey = YYYY-MM-DD`). Daily partitioning keeps the serialisation lock short instead of one global bottleneck.
- Chain head per day is written to `AuditChainCheckpoint` by a nightly job that re-walks and re-verifies the day; a mismatch raises a CRITICAL alert.
- Optional (recommended for a regulated customer): publish the daily head hash to an append-only external store (S3 Object Lock / WORM bucket) so tampering is detectable even by a DB superuser.

### 3.4 Database-level immutability

Migration SQL:

```sql
CREATE OR REPLACE FUNCTION qk_audit_immutable() RETURNS trigger AS $$
BEGIN RAISE EXCEPTION 'audit trail is append-only (%.%)', TG_TABLE_SCHEMA, TG_TABLE_NAME; END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_no_update BEFORE UPDATE OR DELETE ON "AuditTrailEntry"
  FOR EACH ROW EXECUTE FUNCTION qk_audit_immutable();
CREATE TRIGGER esig_no_update  BEFORE UPDATE OR DELETE ON "ESignature"
  FOR EACH ROW EXECUTE FUNCTION qk_audit_immutable();

REVOKE UPDATE, DELETE, TRUNCATE ON "AuditTrailEntry", "ESignature" FROM qk_app;
GRANT INSERT, SELECT ON "AuditTrailEntry", "ESignature" TO qk_app;
```

The application must run as a non-superuser role (`qk_app`) distinct from the migration role. Archival/partition detach runs as a separate maintenance role under change control.

## 4. Implementation plan

### Phase 0 — Foundations (≈3–4 days)

1. **Request context.** `src/lib/audit-context.ts` using `AsyncLocalStorage`; `src/middleware/audit-context.ts` populates it after `requireAuth` with user identity snapshot, `sessionId`, `ip` (behind `app.set('trust proxy', …)`), `userAgent`, `requestId` (uuid, also returned as `X-Request-Id`).
2. **JWT**: add `sessionId` + `name` to `JwtPayload` ([jwt.ts](../backend/src/lib/jwt.ts)); issue a `UserSession` row at login so logout/expiry are attributable.
3. **Schema migration** for the new columns/enums/models above (all additive, nullable).
4. **Immutability migration** (triggers + grants) and a `qk_app` DB role; document the role split in `docs/SECURITY_RUNBOOK.md`.
5. **Rewrite `writeTrail`** in [compliance.service.ts](../backend/src/modules/audit/compliance.service.ts): pull identity from context, accept an optional `tx` client, compute the hash chain, and **stop swallowing errors** — throw, so the surrounding transaction rolls back (fixes G3/G4). Keep the current signature working via optional args.

### Phase 1 — Automatic capture (≈4–5 days)

6. `src/lib/audit-prisma-extension.ts`: `prisma.$extends` intercepting `create/createMany/update/updateMany/upsert/delete/deleteMany` for models in a **GxP scope registry** (`src/lib/audit-scope.ts` — model → module, criticality, PII/secret fields to redact, label field).
7. For `update`/`delete`, fetch the before-image inside the same interactive transaction; emit per-field diffs for scalar changes, a `diff` JSON for the rest. Redact `passwordHash`, `signaturePinHash`, tokens.
8. Exclusions (no audit noise): `SlaTimer` ticks, `FormDraft`, session heartbeats, `AuditTrailEntry`/`ESignature` themselves, read-model caches. Every exclusion is listed with a justification in the validation package — silence must be deliberate and documented.
9. Delete the now-redundant hand-written `writeTrail` calls only where the extension supersedes them (avoid double entries); keep the ones carrying business meaning.

### Phase 2 — Semantic + security events (≈4 days)

10. **Workflow/ticket** (biggest gap): stage transitions, assignment, hold/resume, reopen, cancel, parallel-branch spawn, child-workflow trigger, form submission, approval/rejection — emitted from `ticket.service.ts`, `workflow/engine/orchestrator.ts`, `approval.layer.ts`, `stage-form.service.ts`.
11. **Workflow configuration** changes (a config change alters how every future record behaves — always `CRITICAL`): `workflow.builder.ts`, `stage-form`, `sla`, `approval` policies, `business-calendar`.
12. **Security**: login success/failure/lockout/logout, password change, PIN enrolment, role assignment, permission grant/revoke, user activate/deactivate, site/org changes — `auth.service.ts`, `user.service.ts`, `role`, `permission`, `access`, `site`, `organization`.
13. **Jobs**: `ActorType.JOB` context wrapper for `jobs/worker.ts`, `sla-sweep`, `audit-sweep` (fixes G17).
14. **Access events** for controlled data: document view/download, CoA export, report generation, bulk export (G18) — `VIEW` only for controlled/critical entities, never for list pages, or the trail becomes unreadable.

**Design change — synchronous chaining removed (2026-07-24).** The Phase 0 design hashed each entry on the write path, serialising writers behind `pg_advisory_xact_lock` per UTC day. That lock is **transaction-scoped**, so once Phase 2 made `emitAuditEvent` join the caller's transaction, the lock was held for the caller's *entire* duration — a single in-flight workflow transition blocked every other audit write in the application. Observed live: one backend `idle in transaction` holding the lock with four queued behind it, and all logins hanging. Opening a second transaction per entry also consumed a second pool connection while the business write held the first, compounding it into pool starvation.

Replaced with **write-then-seal**:

- `recordAudit` inserts unsealed (`hash`/`prevHash` NULL), joins the caller's transaction when there is one, and never opens its own. No lock on the request path.
- `lib/audit-seal.ts` chains the unsealed tail in `seq` order under its own session-scoped advisory lock, taken and released by the sealer alone. Runs every `AUDIT_SEAL_INTERVAL_MS` (default 30 s) from the API process — not the BullMQ worker, since that needs Redis and is optional, and the size of the unsealed window is a compliance property.
- Migration `20260724090000_audit_chain_async_seal` narrows the trigger to permit exactly one transition: NULL hash becoming non-NULL with every other column byte-identical (`to_jsonb(OLD) - seal columns = to_jsonb(NEW) - seal columns`). Business-column UPDATE, re-sealing, and DELETE all remain rejected — verified.

What this trades: entries are covered by the append-only triggers immediately, but by the chain only once sealed. The chain is the second line of defence — it detects tampering that bypasses the triggers entirely (superuser disabling them, or files edited under the database) — so the unsealed window is a gap in that secondary control only. Keep the interval short and state the window in the validation package.

Two facts for the validation package, both verified rather than assumed:

- **`seq` is monotonic but not gap-free.** A rolled-back transaction consumes its sequence value; one such gap already exists. A missing `seq` is therefore *not* evidence of deletion — the hash chain is what detects removal. The original schema comment claimed gap-free ordering and has been corrected.
- **Three chain breaks exist at seq 2045/2089/2133**, confined to the boundary where entries sealed by the old synchronous code meet entries sealed by the new sealer. They are an artifact of changing regimes mid-dataset on a development copy, not tampering. All 597 entries written since: **0 breaks**. A production deployment starts clean from the migration point; re-sealing the affected rows is blocked by the trigger and would need a change-controlled operation.

### Phase 3 — Reason for change & e-signature hardening (≈3 days)

15. `reason` becomes **mandatory** for: any change to an approved/effective/closed record, result value changes, spec/limit changes, deletions, retrospective date edits, RBAC changes. Enforced in a `requireReason` middleware reading `X-Change-Reason` or `body.reason`, with a controlled `reasonCode` list.
16. Client: shared `ReasonForChangeModal` wired into the existing edit flows (mirrors the `useConfirmDelete` convention already used for deletes).
17. E-signature: two-component authentication on the first signing of a session (userid + password/PIN) and single-component thereafter per §11.200(a)(1)(ii) with session binding; bind `recordHash`; controlled `meaningCode`; render the signature manifestation (printed name, date/time with timezone, meaning) on every generated PDF (§11.50).

### Phase 4 — Review, export, retention (≈4–5 days)

18. **Backend**: `GET /api/audit-trail` with filters (date range, user, module, entityType/Id, action, criticality, site) + keyset pagination; `GET /api/audit-trail/export` (CSV + PDF, itself audited as `EXPORT`); `GET /api/audit-trail/verify` (chain status); `POST /api/audit-trail/reviews` (periodic review + e-sign). New permissions: `audit_trail.read`, `audit_trail.export`, `audit_trail.review` — replacing the misuse of `audit_register.read` (G15). Trail reads are **site-scoped** like the rest of the app.
19. **Frontend**: `client/src/features/admin/audit-trail/` — global viewer with filter bar, diff rendering (old → new), criticality badges, chain-verification banner, export button; plus a reusable `<EntityAuditTrail entityType entityId />` "History" tab dropped into ticket, document, CAPA, sample, result and course detail pages.
20. **Retention**: monthly partitions on `createdAt`; archive job detaches partitions older than the retention period to compressed WORM storage with a documented, *tested* restore procedure. Retention ≥ the longest record-retention obligation (typically product life + 1 yr, or 10 yr GMP) — confirm with QA before coding a number.
21. **Nightly chain verification** job + alert on failure; weekly digest of CRITICAL events to QA.

**Phase 4 (viewer) status — implemented 2026-07-24.** Pulled ahead of Phase 3: a trail nobody can read is not evidence, and the viewer is also the fastest way to confirm Phases 0–2 actually work.

- **Backend** — `audit-trail.service.ts` / `.controller.ts`, mounted in `audit.routes.ts`: filtered + paginated list, per-record history, filter facets, chain-verification status, CSV export. New permissions `audit_trail.read` / `audit_trail.export`, replacing the misuse of `audit_register.read` (gap G15). CSV export is itself recorded as an `EXPORT` event.
- **Frontend** — `features/admin/audit-trail/AuditTrailPage.tsx` (global viewer at `/admin/audit-trail`, Compliance group in the sidebar) and `components/shared/EntityAuditTrail.tsx`, a reusable History panel now on the ticket and document detail pages. Both render the same row shape so they cannot drift.

Verified live: 2,741 entries listed, ticket history showing `TRANSITION → TICKET_RESUMED` and `UPDATE isOnHold true → false`, CSV export 503 KB, and the export appearing in the trail moments later.

**The integrity banner currently shows a warning**, because `verifyChain` honestly reports the three known discontinuities at seq 2045/2089/2133 (documented above — a development artifact of changing sealing regimes, not tampering). It will read green on a database whose trail starts after the migration. Do not "fix" it by softening the check.

Still not built from Phase 4: PDF export, the periodic-review sign-off screen, and retention/partitioning.

### Phase 5 — Validation package (≈3 days, QA-owned)

22. `docs/validation/` — User Requirements Spec (traceability matrix: requirement → ALCOA++ principle → test case), Functional Spec, IQ/OQ/PQ protocols, and a **Part 11 assessment** covering §11.10(a)–(k).
23. Automated evidence: Vitest suites proving (a) no GxP write can succeed without a trail entry, (b) UPDATE/DELETE on the audit table is rejected by the DB, (c) chain verification detects a tampered row, (d) reason enforcement, (e) e-sign re-auth failure paths. These tests *are* the OQ evidence — keep them in `tests/compliance/`.
24. SOPs: audit-trail review SOP, data-integrity policy, incident procedure for a chain-verification failure.

## 5. Risks & decisions to make

| Risk / decision | Recommendation |
|---|---|
| Prisma extension adds a read per update → latency | Accept; scope the registry to GxP models only, and batch-emit. Measure on the ticket list/update hot path before Phase 1 sign-off. |
| Volume growth (every field change is a row) | Monthly partitions from day one; do not retrofit later. |
| Double-entries during migration from hand-written calls | Phase 1 step 9: remove superseded calls in the same PR that enables the extension for that model. |
| Backfilling existing rows | Do **not** fabricate history. Record a documented "audit trail commenced on <date>" system event; pre-existing data is covered by `createdAt/createdById` columns only, and this limitation is stated in the validation package. |
| Chain write contention | Daily chain partitions + advisory lock; if throughput becomes an issue, shard the chain per module. |
| Hosted Postgres without a superuser split | Verify the provider allows role separation and trigger creation before Phase 0 (Render/Supabase both do). |
| Retention duration | QA decision, not an engineering one — needs an answer before Phase 4 step 20. |

## 6. Sequencing summary

Phase 0 → 1 close **Complete/Accurate/Attributable** (the findings an inspector opens with). Phase 2 closes the workflow and security blind spots. Phase 3 closes **Traceable** (why). Phase 4 closes **Legible/Available/Enduring**. Phase 5 turns it into defensible evidence. Roughly **4–5 weeks** of engineering plus QA time, and Phases 0–1 alone move the system from "partially audited" to "structurally cannot lose an audit record".
